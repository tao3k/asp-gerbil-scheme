#+title: Executable Macro Source Witness Policy
#+startup: overview

* Status

Policy 011 treats collected source as the authority for macro evidence.  A
package manifest may identify dependencies, but it cannot admit a macro edit.

* Admission rule

A runtime macro is admitted only when one collected source owner contains both:

- a parser-owned call or top-level form for that macro; and
- a parser-owned executable assertion such as =check=, =check-equal?=,
  =check-exception=, or =check-output=.

The two facts must belong to the same owner.  A declaration, comment, unrelated
test, or =gerbil.pkg= metadata entry is not a witness.

#+begin_src mermaid
flowchart LR
  M[Runtime macro fact] --> C{Collected owner calls macro?}
  C -- no --> R[Reject with Policy 011]
  C -- yes --> A{Same owner has executable assertion?}
  A -- no --> R
  A -- yes --> P[Admit macro source]
  G[gerbil.pkg metadata] -. dependency identity only .-> C
#+end_src

* Ownership boundaries

- The Gerbil parser owns macro, call, top-form, path, and selector facts.
- The Policy 011 implementation only composes those immutable facts.
- =build.ss= and the ASP Build API own source coverage and invoke the policy
  once for the complete build graph.
- =gerbil.pkg= continues to own package identity and dependency acquisition.
- Gerbil's upstream compiler and =std/make= retain compilation and scheduling
  authority.

* Required scenarios

1. A macro call without an assertion is rejected.
2. A macro call and assertion in the same collected owner are accepted.
3. An assertion in an owner that does not call the macro is rejected.
4. Policy details direct the developer to executable source evidence and never
   recommend package metadata as an escape.

* Performance constraint

Source discovery and parser extraction remain single-pass Build API work.  The
policy consumes the resulting in-memory facts and must not rescan the filesystem,
spawn a compiler, or evaluate Scheme source during admission.
