Compiler 全量构建慢与 ASP 包构建慢需要分别计量。
普通 =gerbil build= 不会重新构建 Gambit、stage0、stage1 或 libgerbil。
本次未运行 compiler 全量 rebuild，也未执行全部 compiler 测试。
根 =make check= 经 =build.sh= 在 src 环境递归 =./...=，而 CI 显式选择
=src/gerbil/test/... src/std/... src/lang/... src/tools/...=。
两种测试入口的目录范围不是同一个契约；tutorial、misc、发行包也有独立
构建示例，不应自动并入 ASP 的日常门禁。
=dist/docker/image.mk= 显式使用 =--no-cache= 构建各发行版容器，
=src/build/build-release.ss= 的 tarball helper 也走 configure / make / install。
这些命令本来就是发行构建，不适合作为包增量性能样本。

** 原生 no-op 仍需要导入模块

已安装 =src/std/make.ss:207= 的 =make-build= 先建立 completion table，
=module-id= 在检查 =build?= 前导入源码。Coordinator 再利用真实 import graph
等待依赖和判断时间戳。=import/mx= 将导入串行化。

同一进程的 module registry 会缓存导入；多次调用 =import-module= 不等于同一
模块被展开多次。但每个新进程重建 registry，所以磁盘产物齐全也不意味着
启动和依赖判定零成本。简单地移除 ASP 声明层不能消除这个原生阶段。

=std/make= 文档仍介绍 =build-deps:= 缓存和 =force:= 行为；安装源码中这些
字段被接受及保存，但 =make-build= 的 currentness 路径未消费它们。
不能以“打开文档中的缓存选项”作为已成立的性能修复。
单模块实验还确认：=force: #t= 返回成功，打印源码 expansion witness，
没有打印 compile 事件，未实现文档所描述的强制重新编译。

本次另以原生 =std/make= 单模块 witness 验证：冷构建成功后，fresh-process
重复构建仍打印 =SOURCE-EXPANSION-WITNESS=，没有 =compile example=。
即使 native 编译被跳过，源码 expansion 阶段仍实际执行。

** 中断恢复的产物完整性

首次全库构建达到测量上限，后端被终止；随后 =gerbil build= exit 0，
没有重新编译。检查 207 个 =.ssi= 对应路径，仍有 11 个缺失 =.o1=。
=gxc-outputs=（安装源码 =std/make.ss:493=）只列 =.ssi= 和 static =.scm=。
这是本次发现的恢复完整性缺陷；“重复 build 成功”不能证明 native 产物完整。
需要在原生 owner 修复 currentness 或加入成功完成全部后端的 receipt，
并覆盖中断、失败、产物删除、正常 no-op 的场景。
11 个主模块恢复后，所有主模块 .o1 均存在，但真正运行时导入仍失败：
=agent-basic~0.scm= 被源码 loader 当作 Gerbil 表达式加载，报
=Bad syntax; illegal expression=，指向生成的 =declare=。
扩大到生成的所有 416 个 .scm 后发现另外 4 个 =~0.o1= 缺失。
完整性检查必须覆盖 phase sidecars，而不止主模块。恢复终态见最终执行补充。

* ASP Building API

** 已确认的边界

- 根 =build.ss= 经 source-relative bootstrap 生成 POO PackageSpec，交给
  =defbuild-script= / =std/make=；本次投影为 207 个库目标。
- 下游的 public-entry closure 是另一个范围，不能把本仓库全库的 207 个
  目标当作每个下游消费者的启动闭包。
- =src/build-api/package-spec.ss:179= 的普通构建不执行完整 parser / policy。
  完整 policy 仅在 =ASP_GERBIL_SCHEME_POLICY=1= 且命令允许时加载。
- 普通投影仍先对所有目标解析源码路径、检查存在并去重，然后才判断 policy
  是否开启。这是可删减的额外工作；现有证据尚未表明它是主要瓶颈。
- =native-profile.ss= 的 provider prepare 可能调用 =brew --prefix= 与
  =pkg-config=。meta/spec 也先求值 BuildSpec；这类外部进程需要独立观测。
  当前纯库投影没有这项 provider 准备成本。
- =just rebuild= 明确执行 clean → deps → build → test。把它用作日常增量
  命令会主动丢弃产物并加入依赖生命周期，不能据此评价 =just build= no-op。

** 修复优先级

1. 给进程启动、源码导入、spec 投影、currentness、Scheme 编译、native 编译
   分别提供 CPU / wall / GC / allocation 观测；当前投影事件在导入之后，
   无法解释 first-output 之前的等待。
2. policy 关闭时跳过其 target-to-source 路径投影，保留相同 native BuildSpec。
3. 在原生 =std/make= owner 上验证导入/currentness 优化：单进程上下文复用，
   或版本、参数、import 及源码变化均绑定的持久缓存。不能按文件名猜依赖。
4. 对 provider 的外部准备保存明确输入的结果，先用匹配的 provider spec
   测量验证，再决定是否缓存。

* ASP 测试系统

** 测试命令包含不同成本

=just test= 是一次原生 =gerbil test=，传入 16 个明确文件。
它不是默认按文件启动 16 次 ASP runner。
这次 harness 的内容还包含：

- startup scenario 的三对 fresh-process 探针；
- batch scenario 的预热、四次串行、batch、handoff 及失败路径子进程；
- =t/project-policy-test.ss= 的完整项目 policy gate。

所以“测试时间”混合了语义测试、进程启动实验、性能断言和全项目解析。
=just check= 先执行 selected-source policy build，再执行含 full-project policy
的测试。两次 scope 与 evidence-complete 参数不同，存在重叠，也各自有语义。
去重必须先证明门禁覆盖等价。

** 发现范围与过滤时机

=src/testing/discovery-runner.ss:38= 默认从 package root 遍历，遇到任何 =t=
目录后递归选择 =-test.ss=。本次默认返回 151 个文件，均在 =./t/= 下，
包括 fixture 和场景中的测试；其范围与 canonical 16 文件列表明显不同。

该实现仅在遍历时跳过 basename =dep=；POO =ignoreDirectories= 在完整
收集后过滤，因此不会减少被忽略目录的遍历和 stat。它还可能进入可见的
嵌套包。此次不能声称扫描了 =.git= 或 =.gerbil=：实际默认目录枚举未将
这些隐藏目录纳入结果，也未选入本地安装依赖的测试。

建议先定义 package-owned 测试根与显式选择契约，在递归前应用经过验证的
POO discovery 边界。增加可执行场景覆盖 fixture、可见嵌套包、隐藏目录、
ignored subtree 和显式文件参数，不依赖下游项目名作规则触发。

** 子进程 batch 的真实代价

=src/testing/extension.ss:577= 将兼容文件分组，使用 workgroup 并发启动
原生 gxtest 子进程；每个进程重新加载其 import closure。当前按文件数和
runtime options 分组，没有按照共享重型 closure 或运行时间做调度。
12 个 batch 可能重复 12 次同一重型导入。

现有 batch 比较使用四个小 fixture，证明的是该 fixture 的启动摊销，
没有证明真实共享 parser/policy 项目在 12 进程时更快。
保留 POO 资源和隔离声明，增加共享 import、独立计算及长短任务混合的
场景，再比较单 harness 与多 batch 的 CPU、wall、RSS、GC。

** 文档与实现漂移

=51.06-gerbil-upstream-testing-audit.org= 声称旧 discovery / selection /
execution owner 已退役且只保留 instrumentation。当前 public
=testing-runner-api.ss= 导出 discovery runner，extension 实际负责 selection、
batch subprocess execution 和进度 receipt。

应明确这些层的当前责任与 canonical entry，而不是凭旧文档继续宣称只有
profile。最终 suite 加载、setup/cleanup、执行结果仍由 gxtest / std/test 所有。

* Parser 与性能证据

已安装运行时探针返回 =(12 1 #t)=：CPU count 12，VM processor count 1，
SMP 编译支持为真。=src/parser/parse-workers.ss:103= 使用 =spawn/name=
创建 green threads，没有为这次解析增加 VM processors。

=parse-worker-phase-row= 将 =workerCount > 1= 直接记录为 =parallel=#t=。
在当前运行时，这只能说明多个任务交错，不能证明 CPU 解析并行。
应记录 VM processor count、并区分 concurrency 与实测 CPU parallelism；
再用 parser-owned workload 验证多 processor 的正确性和收益。
这不影响原生编译子进程：本次快照确实观察到 12 个并发 gsc。

此外 =parse-source-files/profile= 是逐文件解析并每文件 =##gc= 的诊断路径，
普通路径则使用 green-thread mailbox。不能把 profile 总时间直接作为普通
并发路径的性能，也不能用诊断路径的热点占比推断日常门禁。

* 结论

最先修复的是 native currentness 的完整后端产物与失败恢复契约、
=force:= 的实现/文档差异，再处理成本与门禁的分层、discovery 的范围/剪枝、并行性 receipt 的
准确性、工具链及文档漂移。上游的 fresh-process import/currentness 是
Building API 必须单独计量的底层成本。
现有证据不足以把整体慢归因于宏层数、POO 风格或“代码规范不够严格”；
进一步加全项目扫描型规则可能继续扩大门禁成本。
每项新 style rule 仍需 parser facts、policy scenario、benchmark metadata、
focused test 和 aggregate wiring，不能用 allow-list 或抑制警告替代修复。

** 新发现：测试 CLI 的退出码失真

已安装 =gerbil test= 执行现有 =failure-fixture.ss=，断言 =1 => 2=
明确失败，却返回 exit 0，并打印 =MODULE-OK= / =HARNESS-OK=。
=src/gerbil/main.ss= 的 =tool-main= 调用工具入口后返回结果，没有将
=gxtest= 的整数结果转成进程退出码。交互方式显式 =exit= 同一工具结果时，
负例返回 42，正例返回 0。

因此，=asp-full-check=（545.98 秒）与 =asp-final-check=（401.20 秒）
虽退出 0，不能视为通过。它们没有终态 =OK=，真实断言错误被 CLI 状态掩盖。
后续 =qualified-final-check= 使用修正后的入口，正确退出 42。
没有把前两次“绿灯”或 =HARNESS-OK= 当成有效资格证据。

已修改 Justfile、CI 和 onboarding 命令：在一个 =gxi= 进程里调用
