** Native no-op builds still import source

Installed =src/std/make.ss:207= constructs a completion table. =module-id=
imports source before checking =build?=. The coordinator waits for dependencies
and checks timestamps using the real import graph; =import/mx= serializes imports.

A process's module registry caches imports, so repeated =import-module= calls do
not imply repeated expansion. Each fresh process reconstructs that registry,
however. Complete disk outputs do not eliminate startup/dependency costs.
Removing ASP's declaration layer alone cannot remove this native phase.

The =std/make= documentation describes =build-deps:= caching and =force:=.
Installed source accepts and stores these settings, but its freshness path does
not consume them. Enabling a documented cache option is therefore not an
established performance fix. A single-module probe returned success with
=force: #t= and printed an expansion witness without a compile event.
A separate cold/warm probe confirmed that a fresh warm process still prints
=SOURCE-EXPANSION-WITNESS= without =compile example=: expansion executes even
when native compilation is skipped.

* ASP Building API

** Confirmed boundaries in the initial snapshot

- Root =build.ss= creates a POO PackageSpec through source-relative bootstrap,
  then delegates to =defbuild-script= / =std/make=: 207 library targets here.
- A downstream public-entry closure has a separate scope. These 207 targets are
  not every consumer's startup closure.
- Ordinary =src/build-api/package-spec.ss:179= builds do not run the full parser
  or policy. Full policy loads only when =ASP_GERBIL_SCHEME_POLICY=1= and the
  selected command permits it.
- Initially, ordinary projection resolved all target source paths, checked their
  existence, and deduplicated them before checking whether policy was enabled.
  This was removable overhead, without evidence that it dominated startup.
- Provider preparation in =native-profile.ss= can invoke =brew --prefix= and
  =pkg-config=. Meta/spec also evaluates BuildSpec first. Those external process
  costs need separate observation; this pure library projection has no provider
  preparation cost.
- =just rebuild= explicitly runs clean -> deps -> build -> test. It discards
  outputs and includes dependency lifecycle; it is not a =just build= no-op sample.

** Repair priorities

1. Measure CPU, wall, GC, and allocation separately for startup, source import,
   spec projection, freshness, Scheme compilation, and native compilation.
   Projection events occur after import and cannot explain earlier silence.
2. Skip policy's target-to-source projection when policy is disabled, preserving
   the native BuildSpec.
3. Investigate native =std/make= context reuse or persistent caches bound to
   compiler identity, options, imports, and source changes. Do not infer
   dependencies from filenames.
4. Measure provider preparation with a matching spec before deciding whether to
   cache its results and explicitly bound inputs.

** Discovery scope and filter timing

Initial =src/testing/discovery-runner.ss:38= walked from the package root and
selected =-test.ss= recursively once it encountered a =t= directory. It returned
151 files, all under =./t/=, including fixtures and scenario tests: a different

collection, so ignored directories still incurred traversal/stat costs. It could
also enter visible nested packages. This audit did not establish scanning of
=.git= or =.gerbil=: default enumeration did not include those hidden directories
or installed dependency tests.

Define package-owned roots and explicit selection, then apply validated POO
boundaries before recursion. Scenarios should cover fixtures, visible nested
packages, hidden directories, ignored subtrees, and explicit file arguments,
without downstream project names as rule triggers.

** Native batch subprocess costs

=src/testing/extension.ss:577= groups compatible files and uses a workgroup to
launch native gxtest subprocesses concurrently. Each reloads its import closure.
Grouping uses file counts and runtime options, not shared expensive closures or
measured duration. Twelve batches can reload the same closure twelve times.

The four small fixtures establish startup amortization for that fixture set,
not faster execution of a real shared parser/policy workload in 12 processes.
Preserve POO resource/isolation declarations; compare one harness and multiple
batches for shared imports, independent computation, and mixed durations using
CPU, wall, RSS, and GC measurements.

* Initial conclusions

Prioritize native backend completeness, failure recovery, and the =force:=
implementation/documentation mismatch. Then address cost/gate separation,
discovery scope/pruning, parallelism receipts, and toolchain/documentation drift.
Fresh-process import/freshness is a native cost the Building API must measure.
Evidence does not attribute overall slowness to macro depth, POO style, or weak
style enforcement. More whole-project scanning rules could increase gate costs.
Every new style rule still requires parser facts, a policy scenario, benchmark
metadata, a focused test, and aggregate wiring; allow-lists or suppressed warnings
are not substitutes for source/parser repairs.

** 31.11.150 Publication Fencing And Application Closure
The next experiment uses the same repaired installed source and private outputs,
with two native application modules: =publication/app= imports =publication/dep=.
Generation A returns 42 and B returns 43. A controlled old publisher pauses after
checking its authority token. B obtains a newer token and publishes successfully.

Atomic replacement alone permits A to overwrite B on resumption, changing the
fresh selector reader's result back to 42. Rechecking the token inside the same
advisory lock used for grants and publication rejects A with exit 70 and preserves
B's selector bytes and runtime 43. Fresh readers pinned to B continue returning 43
in both controls. These are cooperating Python publication processes; no claim
of fencing untrusted writers or distributed storage is made.

An entry module receipt does not bind a whole application closure. Removing B's
dependency files while retaining its app receipt permits a fresh import through
an explicitly supplied fallback dependency root, returning 101. A broker manifest
with an explicit two-node dependency graph and six artifact hashes per module
rejects an omitted graph node, incomplete inventory, absent dependency files, and
a dependency object changed after sealing. Each rejection preserves the previous
active selector. Complete B is admitted and returns 43; replaying the successful
token is rejected in the uninterrupted broker run.

The graph is fixture-owned, not extracted from general Gerbil imports. Installed
runtime dependencies are external. Admission assumes successful trusted build
completion and quiescent generation roots: hashes do not establish provenance or
prevent mutation after validation. Authority and selector are separate atomic
file replacements without durability synchronization, so crash-consistent token
consumption and publication are not established. These controls also do not
exercise a live process changing its Gerbil module cache, reader retention,
namespace replacement, general closure extraction, or garbage collection.

Evidence: =31.21-native-publication-closure-study.json=, =publication.py=, and
=just audit-native-publication=. Retained compiler patches and deployment remain
unchanged. Prior compiler and namespace observations are separate evidence.
The next contracts are a crash-consistent authority/selector transaction, explicit
admission trust and immutable storage, parser/compiler-owned dependency closure,
and readers whose pinned generation lifetime is retained before reclamation.


** 31.11.160 Process-Crash Publication Transaction
The previous broker performs two atomic replacements. A new SIGKILL control
pauses after replacing the active selector and before consuming the authority
token. Restart sees active B and token 2 still unspent. A fresh publisher uses
the same token with admitted manifest A, moving native runtime from 43 to 42.
This is a publication-state failure even with immutable generation outputs.

The single-record control commits current authority and active publication
in one =state.json=. A publication binds epoch, request identifier, complete
fixture manifest, and canonical manifest digest. All grants and publications
use one stable advisory lock. The writer fsyncs a unique staging file, replaces
the authoritative state, and fsyncs the parent directory before acknowledgement.

Four checkpoint deaths yield consistent state on restart: before staging and
after staging-file fsync retain A with the newer token unspent; after replacement
and after directory fsync retain B with the token spent. An abandoned staging
file is ignored. Retrying the original request commits B in the first two cases
and returns a replay acknowledgement without rewriting state in the latter two.
Every selected B reader returns 43. A consumed token with a different manifest
or request is rejected; a newer grant also rejects the older token. Missing,
malformed, and inconsistent authoritative records fail closed without reset.

** 31.11.170 Compiler-Owned Application Closure
The closure study replaces a hand-maintained dependency graph with native
expander import facts. It follows =module-context-import= through module-import,
import-set, module-export, and owning context, retaining identity, resolved path,
and relative phase. Source membership comes from an explicit build inventory and
expander identities. Reachability from the app selects six of seven built modules,
covering a renamed selected import, re-export bridge, phase-one import, and its
transitive dependency. The unreachable module is excluded.

Artifact shape also needs compiler evidence. A fixed two-object inventory fails
for the bridge, which has one native object, while the app's compile-time code
produces a third object. A narrow export in the scratch make copy exposes the
retained =native-outputs= structural SSI walker without changing its implementation
or retained patches. The resulting manifest binds 12 objects and 24 interface,
completion, source-snapshot, and interface-snapshot files: 36 files across six
reachable modules. Actual source bytes must match completed source snapshots.

A/B generation imports return 42/43. Removing B's leaf and supplying A as a
fallback permits native runtime 42, but the compiler fact resolves outside the
expected local generation and is rejected. Omitting the transitive phase module
from the artifact inventory is rejected. Changing source after the build also
rejects sealing. This advances both dependency membership and output enumeration
from fixed fixture assumptions to compiler-owned facts.

The explicit external import frontier records and rechecks one installed list
interface hash under a supplied installation root. Implicit language/compiler
state and transitive external runtime/native dependencies remain unbound. The
result is an application closure relative to those external assumptions, not a
hermetic environment. Relative phase facts are preserved without general absolute
phase composition. Source expansion runs authored fixture code in fresh processes
and may execute compile-time code; no untrusted-input sandbox is established.
