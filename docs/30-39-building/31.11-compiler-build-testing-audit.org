** Native no-op builds still import source

Installed =src/std/make.ss:207= constructs a completion table. =module-id=
imports source before checking =build?=. The coordinator waits for dependencies
and checks timestamps using the real import graph; =import/mx= serializes imports.

A process's module registry caches imports, so repeated =import-module= calls do
not imply repeated expansion. Each fresh process reconstructs that registry,
however. Complete disk outputs do not eliminate startup/dependency costs.
Removing ASP's declaration layer alone cannot remove this native phase.

The =std/make= documentation describes =build-deps:= caching and =force:=.
Installed source accepts and stores these settings, but its freshness path does
not consume them. Enabling a documented cache option is therefore not an
established performance fix. A single-module probe returned success with
=force: #t= and printed an expansion witness without a compile event.
A separate cold/warm probe confirmed that a fresh warm process still prints
=SOURCE-EXPANSION-WITNESS= without =compile example=: expansion executes even
when native compilation is skipped.

* ASP Building API

** Confirmed boundaries in the initial snapshot

- Root =build.ss= creates a POO PackageSpec through source-relative bootstrap,
  then delegates to =defbuild-script= / =std/make=: 207 library targets here.
- A downstream public-entry closure has a separate scope. These 207 targets are
  not every consumer's startup closure.
- Ordinary =src/build-api/package-spec.ss:179= builds do not run the full parser
  or policy. Full policy loads only when =ASP_GERBIL_SCHEME_POLICY=1= and the
  selected command permits it.
- Initially, ordinary projection resolved all target source paths, checked their
  existence, and deduplicated them before checking whether policy was enabled.
  This was removable overhead, without evidence that it dominated startup.
- Provider preparation in =native-profile.ss= can invoke =brew --prefix= and
  =pkg-config=. Meta/spec also evaluates BuildSpec first. Those external process
  costs need separate observation; this pure library projection has no provider
  preparation cost.
- =just rebuild= explicitly runs clean -> deps -> build -> test. It discards
  outputs and includes dependency lifecycle; it is not a =just build= no-op sample.

** Repair priorities

1. Measure CPU, wall, GC, and allocation separately for startup, source import,
   spec projection, freshness, Scheme compilation, and native compilation.
   Projection events occur after import and cannot explain earlier silence.
2. Skip policy's target-to-source projection when policy is disabled, preserving
   the native BuildSpec.
3. Investigate native =std/make= context reuse or persistent caches bound to
   compiler identity, options, imports, and source changes. Do not infer
   dependencies from filenames.
4. Measure provider preparation with a matching spec before deciding whether to
   cache its results and explicitly bound inputs.

** Discovery scope and filter timing

Initial =src/testing/discovery-runner.ss:38= walked from the package root and
selected =-test.ss= recursively once it encountered a =t= directory. It returned
151 files, all under =./t/=, including fixtures and scenario tests: a different

collection, so ignored directories still incurred traversal/stat costs. It could
also enter visible nested packages. This audit did not establish scanning of
=.git= or =.gerbil=: default enumeration did not include those hidden directories
or installed dependency tests.

Define package-owned roots and explicit selection, then apply validated POO
boundaries before recursion. Scenarios should cover fixtures, visible nested
packages, hidden directories, ignored subtrees, and explicit file arguments,
without downstream project names as rule triggers.

** Native batch subprocess costs

=src/testing/extension.ss:577= groups compatible files and uses a workgroup to
launch native gxtest subprocesses concurrently. Each reloads its import closure.
Grouping uses file counts and runtime options, not shared expensive closures or
measured duration. Twelve batches can reload the same closure twelve times.

The four small fixtures establish startup amortization for that fixture set,
not faster execution of a real shared parser/policy workload in 12 processes.
Preserve POO resource/isolation declarations; compare one harness and multiple
batches for shared imports, independent computation, and mixed durations using
CPU, wall, RSS, and GC measurements.

* Initial conclusions

Prioritize native backend completeness, failure recovery, and the =force:=
implementation/documentation mismatch. Then address cost/gate separation,
discovery scope/pruning, parallelism receipts, and toolchain/documentation drift.
Fresh-process import/freshness is a native cost the Building API must measure.
Evidence does not attribute overall slowness to macro depth, POO style, or weak
style enforcement. More whole-project scanning rules could increase gate costs.
Every new style rule still requires parser facts, a policy scenario, benchmark
metadata, a focused test, and aggregate wiring; allow-lists or suppressed warnings
are not substitutes for source/parser repairs.
