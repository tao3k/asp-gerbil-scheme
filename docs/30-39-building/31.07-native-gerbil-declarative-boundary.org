* 31.07 Native Gerbil Declarative Build and Test Boundary

** Authoritative Entry Points And Responsibilities

Gerbil package projects expose native declarative build entry points:

- =gerbil.pkg= owns package identity, dependency identity, and package policy
  metadata.
- =build.ss= owns the library specification; an explicit product script such
  as =build-provider.ss= owns its executable specification.

Neither entry point delegates package semantics to a component manifest, a
shell pipeline, or a Bazel-specific metadata format.  ASP extends the native
path with policy validation, typed receipts, observability, and test helpers;
it does not replace Gerbil source discovery, compiler scheduling, dependency
installation, or platform flag resolution.  Bazel consumes the two native
entry points as a hermetic cached action and owns only the outer resource guard.

flowchart LR
  Package["gerbil.pkg<br/>identity + dependencies"] --> Gxpkg["gxpkg package lifecycle"]
  Build["build.ss / build-provider.ss<br/>declarative specs"] --> Native["clan/building + std/make"]
  Discovery["clan/building<br/>src discovery"] --> Build
  Flags["cppflags / ldflags<br/>Homebrew fallback on Darwin"] --> Build
  Gxpkg --> Native
  Native --> Artifacts["Gerbil library + explicit executables"]
  ASP["ASP extensions<br/>policy + receipt + observability + gxtest"] -. observes .-> Native
  Bazel["gerbil-bazel<br/>cache + sandbox + outer RSS guard"] --> Package
  Bazel --> Build
  Downstream["Downstream package<br/>package-specific spec only"] --> Package
  Downstream --> Build
#+end_src

Native binding options follow one ordered resolution path in Scheme:

1. Ask =std/make= =cppflags= or =ldflags= for the package.
2. On Darwin, fall back to =brew --prefix= for the requested formula when
   pkg-config metadata is unavailable.
3. Fall back to portable compiler or linker flags that remain valid on Linux.

This resolution is data used by the build spec.  It is not CI-only behavior and
must not be duplicated in Bazel rules or shell launchers.

ASP exposes one downstream declaration macro:
=asp-gerbil-scheme-package-spec!=.  It hygienically expands to native Gerbil
POO =.def= syntax.  The =native-spec= slot holds an ordinary Gerbil build-spec
value; derived package specs use POO =@= inheritance and =previous= to compose
that value.  The macro introduces no replacement keywords for module strings,
=[ssi: ...]=, =[gxc: ...]=, =[gsc: ...]=, or =[exe: ...]=; discovery and
composition continue to use Scheme functions from =std/make= and
=clan/building=.  =asp-gerbil-scheme-package-native-spec= projects the final
list into upstream =init-build-environment!= or =defbuild-script=.
=asp-gerbil-scheme-package-build-profile= projects the package's required
=development= or =production= profile into the same entrypoint; the Building
Framework lowers that semantic value to ordinary =std/make= optimization and
release keys.

The v1 macro surface deliberately rejects a parallel option vocabulary:

| Candidate option | v1 decision | Native Gerbil form retained |
|------------------+-------------+-----------------------------|
| =roots:=         | omit        | =all-gerbil-modules= plus ordinary Scheme filtering |
| =modules:=       | omit        | module strings in the build spec |
| =interfaces:=    | omit        | =[ssi: ...]= |
| =before:=        | omit        | list order and =append= |
| =after:=         | omit        | list order and =append= |

The top-level =build-api.ss= module owns the single stable public address
=:asp-gerbil-scheme/build-api=.  It is both the source-bootstrap facade used by
this package's =build.ss= and the installed facade used by downstream packages.
Package declarations, Building, Testing, policy, and benchmark helpers are
explicit projections of implementation owners beneath =src/=.  There is no
second installed facade and a downstream =build.ss= must not import internal
=src/= modules one symbol at a time.

=all-gerbil-modules= retains the native downstream call shape and
=clan/building= remains the only source-catalog owner.  After that single
upstream scan, the Build API proves the root is inside a Git worktree with =git
rev-parse=; only then does one =git check-ignore --stdin= invocation filter the
already-discovered candidates.  Untracked and unstaged Scheme files therefore
remain immediate build inputs, while ignored untracked files follow nested
=.gitignore=, =.git/info/exclude=, and standard user excludes.  Tracked files
remain inputs even when an ignore rule later matches their path.  The Build API
does not parse =.gitignore=, make Git own source discovery, or translate Git
patterns into an =exclude-dirs= approximation.  Its initialized default
=exclude-dirs= value is inherited by the POO package prototype, while each
downstream package only appends its domain-specific exclusions.  In a source
archive, the same upstream catalog is used without Git filtering, so Git does
not become a package-build dependency.

** Library-default and explicit provider target

Gerbil package installation selects one build script per package through the
=build:= field in =gerbil.pkg= and invokes that script's =compile= command.
=gxpkg= does not propagate consumer-selected feature names; its forwarded build
options are release, optimized, and debug modes.  Therefore the root
=asp-gerbil-scheme= package keeps =build.ss= library-only.  The ASP provider,
HTTP server, and TLS-linked executable are owned by the explicit
=build-provider.ss= entrypoint and the corresponding Bazel target.

The Bazel projection preserves the same boundary in its action inputs:
=//:compile= consumes =library_sources=, while =//:provider_compile= consumes
the full project sources and declares =//:compile= as a dependency.  Provider,
HTTP, or provider product-entry edits therefore do not invalidate the default
library compile cache.

Native CI preserves the same ownership boundary with two independent targets.
The ordinary library target declares logical package dependencies
=("clan" "clan/poo")= to =init-build-environment!= and uses its upstream
default optimized compilation.  Physical acquisition remains solely in
=gerbil.pkg=, whose direct =gerbil-poo= locator transitively owns
=gerbil-utils=.  The provider target uses the =production= profile and owns the
provider binary and HTTP process test.  They run in separate jobs and therefore
never reuse native outputs across profiles; Gerbil =std/make= freshness is
based on source/output state and is not an options-identity cache.

The library declaration covers the complete package API, while the provider
declaration contains exactly 25 project runtime modules and one executable.
Compiling the full library before building that provider is therefore not a
provider optimization: it compiles policy, testing, build tooling, and other
modules outside the provider owner graph. Each target owns its own artifact
root and may share only installed dependency packages.

flowchart LR
    Manifest["gerbil.pkg<br/>physical gerbil-poo locator"] --> Gxpkg[gxpkg dependency installation]
    Gxpkg --> Clan[clan]
    Gxpkg --> POO[clan/poo]
    Source[ASP source checkout] --> Library[Library development target<br/>complete package API]
    Source --> Provider[Provider production target<br/>25 runtime modules + 1 executable]
    Clan --> Library
    POO --> Library
    Deps --> Provider
    Library --> LibraryTests[Semantic library tests]
    Provider --> ProviderTest[Provider HTTP binary test]
    Library -. isolated native outputs .-> Provider
#+end_src

The reusable POO parent lives in =src/build-api/package-spec.ss=, which is an
ordinary import-safe Gerbil module.  Root =build.ss= and top-level
=provider-package-spec.ss= each declare a concrete object derived from that
library prototype.  The provider must not import =build.ss=: upstream
=defbuild-script= expands through the script-context =this-source-file=
binding, so a build entrypoint is not a library module.  Bazel's explicit
=//:provider_compile -> //:compile= dependency is the execution dependency;
POO inheritance supplies the shared semantic contract.

The =production= profile does not make an ordinary =compile= silently enter a
whole-program release build. An explicit =compile --release= remains the native
release request. The Build API forwards it to upstream =std/make= after applying
host policy: Darwin uses =optimize:= plus =build-optimized:= but omits
=build-release:=, because the latter requests a static C runtime that Darwin
does not provide. The resulting executable is an optimized =SINGLE_HOST= C
translation unit with dynamic system/TLS linkage. Non-Darwin release keeps the
upstream optimized static-release request.

A clean Darwin release receipt for the 25-module graph completed successfully
in about 10 minutes 43 seconds. During the final GCC 16 translation the process
identified =___SINGLE_HOST= and reached roughly 3.3 GiB RSS. The resulting
13 MiB arm64 Mach-O links the selected OpenSSL dylibs and =libSystem=. The
runtime-closure oracle found exactly 25 ASP project includes, all beneath the
single =build/workspace-provider= artifact root. These are release observations,
not static fixture values or a synthetic memory gate.

flowchart LR

    Choice -->|compile| Separate[Declared separate-AOT default topology]
    Choice -->|compile --release on Darwin| Single[Optimized SINGLE_HOST C unit]

The ordinary library script uses upstream =init-build-environment!=. The
provider script imports the stable Build API =defbuild-script= macro, which
projects the Package Spec's profile and host build environment into the native
spec before delegating one complete graph to upstream =std/make=. On macOS that
profile removes inherited =SDKROOT= and =DEVELOPER_DIR= selectors; workflow
files and project CLIs do not own or reproduce that policy. Both paths leave
compilation, dependency scheduling, and linking to upstream =std/make=. Before either
passes its complete spec to =std/make=, the ASP Build API applies one core value
to both =GERBIL_BUILD_CORES= and Gerbil
0.18.2's already initialized =__available-cores=.  A positive caller override
wins; otherwise Gambit's =##cpu-count= is used.  No shell probe, fixed machine
count, child-process marker, or second scheduler is involved.

A local Gerbil 0.18.2 receipt reproduced the captured values exactly.  With no
environment override, =GERBIL_BUILD_CORES= resolved to zero while
=__available-cores= was one on a 12-logical-CPU host.  Applying the Build API
policy produced =(12 12 12)=; an explicit override produced =(3 3 12)=.  The
following native build emitted multiple pending =execute compile job= units.
CI remains the cold-build acceptance evidence because its checkout does not
reuse the local package output tree.

This is the feature-equivalent boundary for same-repository development:
ordinary =depend:= consumers build only the library package, while the ASP
Server release and CI paths request the provider target explicitly.  If the
provider later needs independent =gxpkg= installation, it requires a distinct
published package identity; =gxpkg= does not resolve a repository subdirectory
as a second package.

** Decision

The harness must not create a build or test CLI. It improves the Gerbil
experience only above the upstream execution boundary:

- =gxi= evaluates the source-root =src/build.ss= directly. The file is not an
  executable shell program and needs no executable permission.
- =clan/building= owns the native multicall entrypoint, =meta=, =spec=, and
  =compile= actions. It delegates the build graph to =std/make=.
- =gxtest= owns test-file discovery, =-test= export discovery, suite selection,
  setup/cleanup, and process exit status.
- =gxpkg env= may supply the local package environment to =gxi= and =gxtest=.
  It is not a second build command and does not dispatch =build.ss=.

The Building and Testing Framework remains a library. It may define data,
receipts, scenario fixtures, and assertion helpers. It must not reimplement
upstream argument parsing, source discovery, test discovery, build scheduling,
or process dispatch.

** Source-Root Declaration

Runtime modules live under =src/=. The only build declaration therefore lives
at =src/build.ss= and uses the public upstream macro:

#+begin_src scheme
;;; -*- Gerbil -*-
(import :clan/building)

(init-build-environment!
  spec: (lambda () '(... standard std/make build specification ...)))
#+end_src

=init-build-environment!= sets the native source root from its own file,
installs the upstream multicall entrypoint, and accepts a declarative spec
procedure. There is no package-root wrapper, executable-bit requirement, or
private upstream API use.

The project command is:

#+begin_src sh
gxpkg env gxi build.ss compile
#+end_src

An FFI package may keep a native =std/make= build spec as data. It may not
turn that into manual compiler or process dispatch.

** Package Module Identity

The package declares =asp-gerbil-scheme=.  Its public module identity is
=:asp-gerbil-scheme/build-api=; =src/= is a repository layout detail and must
never appear in downstream import names.  The top-level facade uses explicit
source-relative imports to bind implementation owners, while internal modules
may keep their own relative or package-qualified implementation edges.

The migration is parser-first.  Native module import facts identify imports
from downstream-owned files and reject =:asp-gerbil-scheme/src/= as a public
dependency.  Upstream namespaces such as =:std/=, =:gerbil/=, =:clan/=, and
=:wr/= remain unchanged.  Moving or splitting files beneath =src/= therefore
does not change the package API; only the top-level facade's explicit export
projection can do so.

** Test Contract

Tests remain ordinary modules with gxtest-compatible =-test= exports. The only
user-facing test forms are native ones:

#+begin_src sh
gxpkg env gxtest t/...
gxpkg env gxtest -r '^policy$' t/...
gxpkg env gxtest t/package-build-test.ss
#+end_src

The Testing Framework may supply assertions, scenario fixtures, and
performance receipt checks. It does not parse a second test CLI or make a
selected file become a broad project run. Suite selection uses gxtest's =-r=
option; file and recursive scope use its normal arguments.

** Framework Boundary

=src/building/= retains typed =BuildProfile= / =BuildRequest= data only where
it improves inspection, receipt construction, or scenario tests. It lowers to
or observes upstream =std/make= work; it is never the package executor.

=src/testing/= retains gxtest-compatible helpers and scenario assertions. Its
performance gate is a gxtest case. There is no =bench= command and no
framework-specific test-runner compatibility layer.

=Justfile= may name repeatable developer workflows, but every recipe invokes
an upstream command directly. A build recipe uses =gxpkg env gxi=; a test
recipe uses =gxpkg env gxtest=. It does not rewrite source paths or command
behavior.

On Darwin, a repository environment can inject =SDKROOT= or =DEVELOPER_DIR=
from a Nix Apple SDK while the installed Homebrew Gerbil runtime invokes its
configured GCC toolchain.  The Scheme build bridge therefore removes only
those two foreign SDK selectors for the dynamic extent of native =std/make=
execution and restores their exact prior values afterward.  It does not choose
a compiler, store an SDK path, mutate the caller permanently, or add a shell
launcher.  Other platforms pass through the caller environment unchanged.

** Downstream Dependency Boundary

A downstream =gerbil.pkg= dependency imports only
=:asp-gerbil-scheme/build-api=.  That facade explicitly projects package
declaration, source discovery, profile projection, Building, Testing, policy,
and benchmark APIs.  It does not import ASP's CLI, provider server, HTTP
runtime, or ASP product-native plan.  Those are ASP product owners, not public
Build API dependencies.

The package macro discovers one module catalog at =build.ss= load time.  Policy
and =std/make= receive projections of that same catalog; policy does not run a
second repository discovery.  Gerbil remains responsible for compiler import
expansion, freshness, dependency ordering, and parallel scheduling.

** Required Deletions

The migration removes:

- the former root =build.ss= dispatcher and its executable-bit requirement;
- bootstrap stage lists, source-interface materialization, and dynamic loading;
- handwritten getopt, =compile= / =install= dispatch, and test subcommands;
- SDK paths, compiler paths, load-path rewriting, and package-manager-specific
  shell dispatch; the Scheme bridge may dynamically exclude only foreign
  Darwin SDK selectors while native =std/make= runs;
- package-local wrappers which only forward to gxtest or std/make.

=native-build.ss= and =gxtest-runner.ss= are retained only where they expose a
real reusable library concern. Any remaining part that serves the removed
command protocol is deleted rather than preserved as compatibility code.

** Migration And Verification

1. Put the upstream =clan/building= declaration in =src/build.ss=.
2. Change build recipes to =gxpkg env gxi src/build.ss compile= and test recipes
   to direct =gxpkg env gxtest= invocations.
3. Replace root test selections with direct gxtest file, recursive, and
   suite-regex arguments while preserving selected-file scope.
4. Add a downstream scenario that invokes a source-root build through =gxi= and
   test modules through =gxtest= using only public library helpers.
5. Extend the build policy to reject handwritten command routing, dynamic
   loading, persistent or hard-coded environment rewriting, and direct compiler
   process dispatch, while accepting the upstream =clan/building= form,
   standard =std/make= FFI data, and the narrowly-scoped Darwin host-toolchain
   selection.
6. Add a parser-fact package-identity gate: no source-relative import may map
   to an owned source module after migration.
7. Keep performance checks as gxtest cases, with declaration/receipt overhead
   measured separately from native compiler work and with explicit units.

** Acceptance Criteria

- =gxpkg env gxi src/build.ss compile= builds without a harness command or
  executable permission.
- =gxpkg env gxtest t/...= runs the full suite, and an explicit file runs only
  that file.
- =src/build.ss= stays a small upstream declaration with no custom runner or
  mutable bootstrap logic.
- Downstream examples use the same native commands and no hidden wrapper.
- Policy and scenario coverage reject reintroduction of a second command
  protocol.
* One Project Catalog, Profile-Owned Test Convention

The public Package Spec declares one explicit source ownership boundary.  A
normal Gerbil project therefore uses =roots: ["."]=.  It does not declare a
second =runtime-roots= catalog.  The Builder Profile owns the conventional
=t/= test root and removes those modules only when projecting the catalog to
the native =std/make= build spec.  Provider static linking remains a separate,
explicit =runtime-modules= projection owned by the Provider Package Spec.
