#+TITLE: 31.05 Declarative Building Macro API
#+STARTUP: overview

* Purpose

The Building Framework is a library, not a project-specific shell recipe.
Downstream =build.ss= files use =building/build-script= for executable builds.
The declarative BuildRequest macros remain the typed plan/receipt surface for
Testing and inspection; they are not a second compiler entry point.

The declaration layer does not schedule compiler workers. Native toolchain
selection, cache admission, and the default host-core projection belong to
Building, while =std/make= owns the dependency graph and consumes
=GERBIL_BUILD_CORES=.

* Dependency Boundary

#+begin_mermaid
flowchart LR
  Script["Downstream build.ss"] --> Bridge["building/build-script"]
  Bridge --> Make["std/make"]
  Decl["typed plan and receipt"] --> Build["building/facade"]
  TestDecl["testing/building"] --> TestModel["testing/model"]
  TestDecl --> Build
  Script --> TestDecl
#+end_mermaid

=building/= has no import of =testing/=.  The Testing-side adapter owns the
projection from a BuildRequest into a performance project, so the edge is
strictly =Testing -> Building=.

* Downstream Form

#+begin_src scheme
(import :asp-gerbil-scheme/src/building/build-script)

(defbuild-script
  (framework-executable-build-spec
   "src/main"
   "example-provider"
   '("src/core" "src/workflow"))
  bindir: (framework-build-bindir))
#+end_src

For typed plan inspection and Testing projection, downstream libraries may also
compose the declarative API:

#+begin_src scheme
(import :asp-gerbil-scheme/src/building/declarative
        :asp-gerbil-scheme/src/testing/building)

(define-std-build project-build
  label: "project-build"
  source: "src"
  make-options: []
  label-of: car
  after: (lambda (_stage _context _result) #!void)
  stage-specs: [["core.ss"] ["workflow.ss"]]
  current?: source-current?
  context: '((environment . caller-owned)))

(define-build-performance-project project-build-matrix
  request: project-build
  fixture-path: "t"
  name: "project-build"
  suite-name: "default"
  suite-names: ["warm" "cold"]
  case-names: ["core" "workflow"]
  roots: ["t"]
  gates: [])
#+end_src

The macros expand to the same functional values exposed by =building/facade=.
The expression forms =std-build= and =build-performance-project= support local
composition when a named binding is not appropriate.

* Guarantees

- A BuildRequest is inspectable before execution and can be projected into a
  receipt without running a compiler.
- Compiler worker count is never duplicated in the declaration. A positive
  =GERBIL_BUILD_CORES= remains authoritative; otherwise the Scheme Framework
  supplies =##cpu-count= before compiler import to the single upstream
  scheduler. The declared runtime-module closure is target data, not another
  scheduler; Gerbil's emitted executable stub is its conformance oracle.
- The Testing projection produces plan-only runners.  Stage execution remains
  an explicit Building operation.
- Multiple suite and case names are mapped functionally, so matrix coverage is
  data-driven rather than an accumulating set of project-specific branches.

* Verification

=t/building-declarative-test.ss= compiles against the public library routes
and verifies named declarations, expression declarations, Testing projection,
and the suite/case matrix with direct GxTest.
